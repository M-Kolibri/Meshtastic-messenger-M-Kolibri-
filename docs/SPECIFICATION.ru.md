# ТЕХНИЧЕСКИЙ ПРОЕКТ ДЕЦЕНТРАЛИЗОВАННОГО МЕССЕНДЖЕРА «M-KOLIBRI»

## 1. Введение и концепция проекта
Проект **«m-kolibri»** представляет собой специализированное программное обеспечение для мобильной платформы Android. Мессенджер предназначен для обеспечения обмена текстовой информацией в полностью децентрализованных mesh-сетях общего назначения (на базе технологии LoRa / аппаратной экосистемы Meshtastic) в условиях полного отсутствия глобальной сети Интернет, сотовой инфраструктуры и промежуточных серверов сигналинга.

Архитектурная идея базируется на двух фундаментальных принципах:
1. **Максимальное сжатие информации** для преодоления жесткого аппаратного лимита пакета LoRa.
2. **Двухэтапная архитектура безопасности:** старт с опорой на штатное шифрование канала Meshtastic в MVP (`v0.1`) и последующее внедрение независимого сквозного шифрования (`E2EE`) на уровне приложения между конечными узлами (`P2P`) без доверенной центральной стороны (`v0.2+`).

Приложение работает с заводскими платами «из коробки» (LilyGO T-Beam, Heltec V3 и др.) под управлением стандартной прошивки Meshtastic. Взаимодействие со смартфонами осуществляется по протоколу Bluetooth (BLE) через официальный API Meshtastic с использованием Google Protocol Buffers (`Protobuf`). Кастомные сжатые данные передаются через выделенный порт приложений (`PortNum.PRIVATE_APP`), что освобождает пользователя от необходимости перепрошивки аппаратных модулей.

## 2. Архитектурный уровень защиты и модель сети: P2P и E2EE
* **P2P (Peer-to-Peer / Одноранговая сеть):** концепция взаимодействия, исключающая наличие выделенных серверов. Все узлы сети обладают равными правами и выполняют функции как клиентов, так и маршрутизаторов. В рамках mesh-сетей P2P-архитектура обеспечивает максимальную отказоустойчивость: отсутствие единой точки отказа делает сеть устойчивой к внешним блокировкам.
* **E2EE (End-to-End Encryption / Сквозное шифрование — Релиз v0.2+):** архитектурный подход, при котором шифрование информации происходит непосредственно на устройстве отправителя, а расшифрование — исключительно на устройстве конечного получателя. Промежуточные узлы mesh-сети (ретрансляторы, пиры) осуществляют лишь транзитную пересылку информационных пакетов, не имея технической возможности получить доступ к открытому тексту сообщений. *(Примечание: в версии MVP v0.1 конфиденциальность в радиоэфире обеспечивается штатным шифрованием канала AES-256-CTR прошивки Meshtastic).*

## 3. Математика словаря и модульная компрессия
Для оптимизации пропускной способности радиоканала применяется оригинальный алгоритм **«Колибри-код»**. Вместо посимвольной передачи слов в кодировке UTF-8, текст преобразуется в фиксированные индексы статической кодовой книги. Масштабирование на сложные языковые группы (китайский, арабский) исключено из базовой разработки ввиду высокой морфологической/сегментационной сложности и полностью делегировано открытому сообществу контрибьюторов.

### 3.1. Англоязычный модуль (`Base32`)
Для кодирования слов английского языка используется трехзначный код в системе счисления по основанию 32 (алфавит включает заглавные латинские буквы и цифры `2–7`). Емкость словаря вычисляется как $32^3$ и составляет **32 768 уникальных словоформ**. Учитывая слабую морфологию английского языка, данного объема достаточно для покрытия широкого лексического запаса, включая технические и специализированные термины. Вес одного токена в пакете строго равен **3 байтам**.

### 3.2. Альтернативный буквенно-цифровой модуль (`Base36`)
В качестве альтернативного или расширенного варианта проектирования словаря может использоваться трехзначный буквенно-цифровой код (латинские буквы `a–z` и цифры `0–9`), формирующий алфавит мощностью 36 символов. Общее число уникальных комбинаций в такой системе составляет $36^3 = \mathbf{46\ 656}$. Данного объема также достаточно для покрытия всего повседневного лексикона английского (или русского) языка, включая сленг и базовые технические термины.

### 3.3. Русскоязычный модуль (Двухуровневый бинарный код)
Богатая морфология, наличие падежей, склонений и спряжений в русском языке делают кодирование целых словоформ неэффективным. Архитектура «m-kolibri» использует **три бинарных байта (24 бита)** на одно слово, разделяя их на две статические таблицы:
* **Таблица основ (Первые 2 байта):** предоставляет $2^{16} = \mathbf{65\ 536}$ комбинаций для хранения неизменяемых начальных форм слов (лемм). Это полностью покрывает активный словарь русского языка.
* **Таблица флексий и окончаний (Третий байт):** предоставляет $2^8 = \mathbf{256}$ комбинаций. Каждый бит или значение байта кодирует грамматический модификатор (падеж, число, род, время глагола). При декомпрессии приложение получателя синтезирует корректную словоформу на основе основы и флексии.

### 3.4. Модульная архитектура, дистрибуция и обработка исключений
Для снижения изначального веса мобильного приложения ядро программы компилируется отдельно. После установки пользователь выбирает необходимую языковую группу, и соответствующий статичный двоичный файл словаря (например, `ru.bin` или `en.bin`) загружается пользователем отдельно.

Каждый пакет содержит уникальный идентификатор версии и **1 байт флага языка/протокола** в заголовке, что позволяет узлам корректно обрабатывать или игнорировать входящие типы данных без рассинхронизации сети при подключении новых участников.

> **Механизм обработки исключений:** при вводе пользователем слов, отсутствующих в статической кодовой книге, приложение использует посимвольное кодирование с применением выделенного управляющего префикса, сигнализирующего модулю декомпрессии о переходе в режим прямого чтения символов.

## 4. Сетевая архитектура и структура физического пакета LoRa
Максимальный размер физического пакета LoRa в экосистеме Meshtastic составляет порядка 230–240 байт (в чистом физическом ограничении кадра некоторых конфигураций — 200 байт). С учетом накладных расходов стандартной прошивки (сетевые заголовки, маршрутизация, Protobuf-контейнер порта `PRIVATE_APP`), под полезную нагрузку «Колибри-кода» выделяется от **150–180 до 183 байт** чистого места на один кадр, что позволяет передавать до **50–61 сжатого слова** в одном сообщении (и до ~65 слов в режиме `v0.1` без заголовков `Nonce`).

### Распределение байт внутри полезной нагрузки структуры кадра (Полная спецификация E2EE)

| Элемент структуры кадра | Размер | Назначение в P2P Mesh-сети |
| :--- | :---: | :--- |
| **Флаги кадра / Код языка** | 1 байт | Версия протокола, флаг режима шифрования (`v0.1` / `v0.2`) и ID словаря. |
| **ID Отправителя** | 4 байта | Локальный уникальный адрес узла-источника. |
| **ID Получателя** | 4 байта | Адрес целевого узла (или `0xFFFFFFFF` для общего канала). |
| **Счетчик пакетов (Nonce)** | 8 байт | Защита криптосистемы от атак повтора пакетов *(режим E2EE v0.2+)*. |
| **Полезная нагрузка** | до 183 байт | Поток сжатых кодов слов (3 байта на слово, до 61 слова в пакете). |

Для безопасной транспортировки пакета от Android к LoRa-модему по Bluetooth используется текстовая инкапсуляция в формат **Base64**. Это предотвращает искажение данных из-за пересечения с управляющими символами протоколов BLE/SPP. Прошивка Meshtastic на плате аппаратно принимает и транслирует данные, очищая их от Base64 перед отправкой в радиоэфир (в бинарный вид).

## 5. Криптографическая защита и протокол безопасности (Релиз v0.2+)
В отсутствие централизованных серверов аутентификации главной задачей становится безопасная генерация общего секретного ключа между двумя независимыми узлами «по воздуху». Протокол безопасности реализуется на базе гибридной схемы:

1. **Согласование общего секрета (`Curve25519`):** выполняется по алгоритму Диффи-Хеллмана на эллиптических кривых (ECDH) с использованием ультракомпактной кривой **Curve25519**. Каждый пользователь генерирует пару ключей — приватный (секретный) и публичный (открытый). Публичные ключи размером **32 байта** передаются между пользователями напрямую в безопасной обстановке через сканирование QR-кодов на экранах смартфонов. Путем математического перемножения своего приватного ключа и чужого публичного ключа оба смартфона получают идентичный секретный ключ сессии. Малый размер ключа (32 байта) критически важен в условиях жесткого ограничения длины пакета LoRa.
2. **Симметричное шифрование:** после выработки общего секрета строка кодов слов шифруется с помощью быстрых алгоритмов симметричного шифрования — поточного шифра **ChaCha20** или блочного алгоритма **AES-256 в режиме счетчика (CTR)**. Главное преимущество данных режимов — сохранение длины данных байт-в-байт после шифрования (**0 байт прироста**), что полностью исключает появление оверхеда и необходимость выравнивания (padding). Для локального хранения сообщений на смартфоне применяется зашифрованная база данных **SQLCipher**.

### Сравнительный анализ применимости симметричных шифров в LoRa/Mesh-сетях

| Критерий / Алгоритм | AES-256 (Режим CTR) | ChaCha20 | Кузнечик (ГОСТ Р 34.12-2015) |
| :--- | :--- | :--- | :--- |
| **Тип шифра** | Блочный (в режиме потока) | Поточный шифр | Блочный шифр |
| **Длина ключа** | 256 бит | 256 бит | 256 бит |
| **Размер пакета на выходе** | Равен исходному (0 байт прироста) | Равен исходному (0 байт прироста) | Кратен 16 байтам (требует padding) |
| **Сложность интеграции** | Низкая (есть в ОС Android) | Низкая (доступны легкие библиотеки) | Высокая (требует сторонний SDK) |
| **Особенности применения** | Поддерживается аппаратно большинством современных процессоров. Высокая криптостойкость. | Ориентирован на программную реализацию. Максимальная скорость на мобильных устройствах и МК без ускорителей. | Использует размер блока 128 бит. Требует обязательной гос. сертификации для госсектора или ОПК РФ. |

## 6. Дорожная карта разработки проекта (Roadmap)
* **Этап 1: Теоретическое проектирование и математический расчет** — фиксация архитектуры, расчет емкости словарей (`Base32` / `Base36` / 24-битный бинарный код), проектирование структуры кадра и спецификаций Protobuf.
* **Этап 2: Сборка аппаратного стенда и проверка радиоканала** — настройка двух плат на базе ESP32+LoRa (LilyGO T-Beam / Heltec V3, диапазоны 868/433 МГц) с официальной прошивкой Meshtastic и тестирование доставки сырых пакетов BLE <-> LoRa.
* **Этап 3 (MVP v0.1): Ядро компрессии и базовый интерфейс** — реализация токенизатора и декомпрессора на Kotlin, подключение словарей `ru.bin` / `en.bin`, создание экрана чата и выпуск первого `.apk` (с использованием штатного шифрования канала AES-256 прошивки Meshtastic).
* **Этап 4 (Релиз v0.2): Сквозное шифрование на уровне приложения (E2EE)** — интеграция фреймворка Bouncy Castle (`Curve25519` ECDH + `ChaCha20` / `AES-256-CTR`), интерфейса обмена QR-ключами и локальной зашифрованной базы данных `SQLCipher`.
* **Этап 5: Публикация Open Source** — размещение релизных сборок `.apk` в **GitHub Releases** и независимом каталоге **F-Droid**.
